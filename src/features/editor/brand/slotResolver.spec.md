# Slot resolver — design spec

> **Status.** Phase 0 contract; Phase 3 step 1 ships
> `brandToBrandKit` (the priority-chain implementation) at
> `src/features/editor/brand/brandToBrandKit.ts`. The slot enum in
> `src/features/editor/schema/index.ts` is the contract. The full
> resolver (`applyBrandToDocument`) is Phase 3 step 2. This document
> is the rationale that contract carries — it tells the future
> contributor *why* each fallback exists, so they can judge edge
> cases without re-deriving from scratch.

## Purpose

A `BrandOSDocument` carries `SlotRef` values inside layers
(`fontFamily`, `color`, `background`, `fillOverrides[k]`). At render
time the brand engine walks the document and replaces every `SlotRef`
with a concrete value resolved against the user's `Brand`. This file
specifies how each slot resolves.

The brand engine reads from the v3 `Brand` schema in
`src/shared/types/brand.ts`. The legacy fields on `Brand` (`primaryColor`,
`secondaryColor`, `fonts`, `neutrals`, etc.) are still present because
not every brand has been migrated to the v3-only fields, and the
deprecation rule is "new writes target v3, reads tolerate both."
The resolver respects that rule: prefer v3, fall back to legacy, never
the other way round.

## Color slots

### `brand.color.primary`

Priority chain:

1. `brand.colorSystem?.primary?.hex` — the v3 canonical surface. Always
   present on a v3-migrated brand because `ColorSystem.primary` is a
   required field.
2. `brand.primaryColor` — the legacy flat string. Always present on
   any `Brand` (the field is non-optional in TypeScript today, even on
   v3-migrated brands, because back-compat consumers still read it).

The fallback to (2) almost never fires in practice on a v3 brand —
both fields will be populated and (1) wins. (2) is the safety net for
unmigrated or partially-migrated brands.

### `brand.color.secondary` and `brand.color.accent`

Same shape:

1. `brand.colorSystem?.secondary?.hex` / `.accent?.hex`
2. `brand.secondaryColor` / `brand.accentColor`

Both are optional everywhere. If the chain yields nothing, the
resolver returns `null` and the consuming layer falls back to its
literal value (or, if the layer has no literal, hides — Phase 3
decides per-layer).

### `brand.color.neutral` (with `neutralIndex`, default 2)

This is the messiest slot because **two unrelated structures** can
both store neutrals on the same brand:

- `brand.colorSystem?.neutrals` — `ColorToken[]` (`{ hex, name?, ... }[]`),
  v3 canonical, populated when the brand was migrated through the v3
  pipeline.
- `brand.neutrals` — `string[]` (raw hex), generated by the Brand Board
  editor's six-shade ramp from the primary hue. Populated whenever a
  brand has been opened in Brand Board.

Both can be present on the same brand. They are not guaranteed to
agree on count (ColorToken[] is variable-length; the Brand Board ramp
is fixed at six). The resolver picks in this order:

1. `brand.colorSystem?.neutrals?.[neutralIndex]?.hex`
2. `brand.neutrals?.[neutralIndex]`

The v3 source wins because Brand Board is a generator — its output is
a derivative ramp, not curated decisions. If a designer chose specific
neutrals via the v3 editor, those are intentional and should beat the
ramp. `neutralIndex` is clamped to the array length the resolver picks
from; out-of-range falls through to the next chain step rather than
returning undefined.

If both sources are missing, the resolver returns the
`buildBrandPalette(brand).bg.subtle` value (v3 brand palette is itself
a fallback layer on top of the brand kit, see
`src/shared/brand/brandPalette.ts`). That keeps a layer-with-neutral
from rendering invisibly.

## Font slots

### `brand.font.heading`

Priority chain:

1. `brand.typescale?.fonts.heading.family` — the newest, most explicit
   source. `Typescale` (`src/shared/types/typescale.ts`) was added
   after the v3 typography fields and explicitly names "heading" and
   "body" pair members. When present, it's authoritative.
2. `brand.typography?.primary.family` — the v3 canonical typography
   field. `primary` historically meant "the heading-ish one" by
   convention but the convention is informal.
3. `brand.fonts.primary` — legacy flat string. Always present on any
   `Brand`.

### `brand.font.body`

Priority chain (longer than heading because the failure mode here is
worse):

1. `brand.typescale?.fonts.body.family` — explicit body font from
   `Typescale`.
2. `brand.typography?.secondary?.family` — v3 typography. `secondary`
   is the convention for "the body-ish one"; optional, often absent.
3. `brand.typography?.primary.family` — falls back to the heading font
   because **a brand with only one font family is a real, common case**
   (especially for utility brands and early-stage brands). Two distinct
   fonts is the design ideal; one font everywhere is the design floor.
4. `brand.fonts.secondary` — legacy.
5. `brand.fonts.primary` — last resort, same family-everywhere logic.

The reason body's chain falls all the way back to the heading family
on the way down: an empty body font is a worse outcome than reusing
the heading font. The text becomes the browser default (Times New
Roman in many contexts), which is jarring and clearly broken.
Reusing the heading font is at least *intentional-looking*. This is
why steps 3 and 5 reach back into the heading chain.

## Logo slots

`brand.logo.primary | .secondary | .wordmark | .iconmark | .mono.black | .mono.white`

These map 1:1 onto `LogoSystemRefs` from
`src/shared/types/brandAssets.ts`:

```
brand.logoSystem.primary       → 'brand.logo.primary'
brand.logoSystem.secondary     → 'brand.logo.secondary'
brand.logoSystem.wordmark      → 'brand.logo.wordmark'
brand.logoSystem.iconmark      → 'brand.logo.iconmark'
brand.logoSystem.mono.black    → 'brand.logo.mono.black'
brand.logoSystem.mono.white    → 'brand.logo.mono.white'
```

Each slot is a `LogoRef` containing an `assetId`. The resolver looks up
`brand.brandAssets[assetId]`, picks the best format (svg > png >
webp > jpg, configurable via `LogoRef.preferredFormat`), and returns
the URL.

If `logoSystem` is missing or the named slot is missing, the resolver
falls back through the legacy `brand.logoAssets.*` shape (`full`,
`icon`, `wordmark`, `dark`, `light`) where the equivalent exists, and
finally to `brand.logo` (the original single-URL field). Same v3-first
rule: legacy reads only, no writes.

The `LogoLayer.variant: 'auto'` value bypasses the slot enum and
routes through `pickLogoOnBackground(brand, bgHex)` from
`src/shared/brand/logoOnBackground.ts`. That function scores every
available logo variant by WCAG contrast against the background and
returns the most readable one — including monos when contrast against
the brand color is poor. `'auto'` is the right default for new layers;
explicit variants exist for designers who want to override.

## Spacing slot

### `brand.spacing.unit`

`brand.uiStyle?.spacing` is one of three named tiers. The resolver
maps tiers to pixel values:

| Tier | Pixels |
|---|---|
| `'compact'` | 4 |
| `'comfortable'` | 8 |
| `'spacious'` | 12 |

`8` is the default when `uiStyle` is missing or `spacing` is undefined
— matching the implicit default everywhere else in BrandOS (the Brand
Board generator picks `comfortable` on first save).

### Adding a new spacing tier

If a designer needs more granularity (`'dense'`, `'airy'`, etc.), the
extension is:

1. Add the tier to `BrandUIStyle.spacing` enum in `brand.ts`.
2. Add the px mapping here.
3. Update the resolver in `applyBrand.ts`.

The named-tier approach (rather than passing arbitrary pixel values
through the slot) is intentional. Slots are brand-relative semantics,
not pixel literals — a `compact` design that's right for a business
card spacing decision is also right for a presentation spacing
decision, even though the absolute pixel might differ. Future
multi-surface tiers (different px per `ContentTypeConfig`) are the
clean upgrade path.

## Surface kinds (BaseLayer.surfaceKind)

When a layer is part of a recognizable composition role — a hero band,
a card, an inverted footer — `surfaceKind` records that role on the
layer. The brand engine then resolves color and text via
`pickSurfaceTokens(buildBrandPalette(brand), surfaceKind)` from
`src/shared/brand/brandPalette.ts` rather than picking each slot
independently. This is what prevents the "all my surfaces are
hand-painted and clash" failure mode the user flagged on
2026-04-25.

`surfaceKind` is optional. When absent, the brand engine resolves
slots one at a time (no surface coordination). Use it when the layer
plays a known compositional role; leave it off for one-off elements.

## Memoization is required, not optional

`brandToBrandKit(brand)` walks the entire priority chain every call.
On a multi-page document with frequent selection changes, calling
this on every render is wasted work that compounds.

**Every React call site MUST memoize via `useBrandKit(brand)`** from
`src/features/editor/brand/useBrandKit.ts`. The hook keys on the
brand reference identity AND `brand.updatedAt` so it catches both
Zustand-style replacements and in-place mutations.

Non-React call sites (services, AI pipeline, headless export)
should memoize per-request: derive the BrandKit once at the boundary
and pass it down. Do NOT call `brandToBrandKit` inside a loop.

If you find yourself reaching for `brandToBrandKit` directly in a
React component, ask whether `useBrandKit` would be the right home
for that call instead.

## Neutrals normalization

`normalizeNeutrals(source)` from `./neutrals.ts` always returns 6
hex strings, lightest → darkest. Behaviour by input length:

| Input length | Output |
|---|---|
| 0 | throws — caller falls back to `suggestNeutrals(primary)` |
| 1 | 6 copies (degenerate; caller should generally avoid) |
| 2..5 | linear HSL interpolation between sorted-by-luminance stops |
| 6 | returned as-is, sorted by luminance |
| 7+ | even-spacing downsample after sort |

The original spec said "pad by repeating the last entry" — that was
rejected during Phase 3 review because it produces visually broken
brands (slots 4/5/6 all rendering as the darkest color). HSL-space
interpolation guarantees a monotonic luminance ramp regardless of
input length.

## Diagnostic warnings

`brandToBrandKit` populates `BrandKit._diagnostics.warnings: string[]`
whenever a fallback is taken at a step where the source brand could
have been more complete. Cases that emit a warning:

- No primary color defined (falling back to `#888888`)
- No neutrals defined (generating ramp from primary hue)
- No body font defined (falling back to heading family) — also
  emits `console.warn` in dev (not prod)

Empty `warnings` is the success case. Phase 3 just populates the
field; future "brand health" UI will display it. The presence of a
warning is not an error — it's a hint that the brand is incomplete.

## What this resolver does NOT do

- It does not handle font *loading* (the editor renders with whatever
  font CSS resolves to; loading non-system fonts is a Phase 1 concern
  for the Fabric adapter and a future Phase concern for headless
  export).
- It does not handle CMYK or Pantone outputs — those come off
  `ColorToken` for print-aware export pipelines. Phase 0 stays in
  hex/RGB land.
- It does not validate readability. `LogoLayer.variant: 'auto'` does,
  via `pickLogoOnBackground`. For colored fills against colored
  backgrounds the validation lives in
  `pickFgOnBackground` and is invoked by the brand engine on a
  per-surface basis (Phase 3).
